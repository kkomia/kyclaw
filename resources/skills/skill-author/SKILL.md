# skill-author：按用户给的信息创建技能 / MCP / 插件

## 什么时候用我

- 用户贴一段安装说明（README、"Installation"、"把下面加进你的 MCP 配置"、一段 `SKILL.md`），要你把它装好。
- 用户说"做个技能，以后我说 X 你就按 Y 做"、"把这份检查清单存成技能"。
- 用户说"这个 MCP 不用了，删掉"。

不要用我：用户只是让你**用**某个已装好的技能（那直接 `use_skill` 读它）；要生成报告/PPT/表格（那用 office 四件套的技能）。

## 一、先判断用户给的是什么

| 用户给的东西                                                                             | 落地方式                                                                                             |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 一段"做法/流程/检查清单"的说明，或明确说"记成技能"                                       | `create_skill`（写进用户技能目录）                                                                   |
| 一段 MCP 配置（JSON 里出现 `command` / `url` / `mcpServers`），或"帮我连上某个 MCP 服务" | `add_mcp_server`（写进设置里的 mcpServers）                                                          |
| 一个**插件**仓库 / 插件目录（有 `.claude-plugin/marketplace.json` 或 `plugin.json`）     | 见第四节：插件只能**由用户在插件页安装**，你不能替他点；你能做的是把目录按约定写出来并告诉他怎么装   |
| 一段 shell 安装命令（`npm install -g` / `pip install` / `curl … \| sh`）                 | **不要照抄来跑**。那是 `bash` 工具的事、要单独审批；先问用户是否真的要在本机装，并把命令原样念给他看 |

判断不了就问一句，不要猜。

## 二、技能：`create_skill`

```
create_skill({
  name: "invoice-helper",                 // 目录名 + frontmatter 的 name：只能小写字母/数字/短横线
  description: "用户要做发票、对账单、报销单时用它：讲清口径与自检清单",  // 写触发词，模型靠它决定要不要读全文
  body: "# 发票助手\n\n## 什么时候用\n…\n## 怎么做\n…\n## 常见坑\n…\n## 交付前自检\n…",
  license: "用户自建技能",                  // 借用他人文本时必须写清出处与许可
  files: [                                 // 可选：reference/*.md、scripts/* 之类
    { path: "reference/fields.md", content: "…" }
  ]
})
```

**名字口径（硬）**：`^[a-z0-9][a-z0-9-]{0,63}$` —— 1-64 位小写字母/数字/短横线，首字符是字母或数字。它同时是目录名与引用名，所以中文 / 空格 / 大写 / 下划线都不行：把「发票助手」写成 `invoice-helper`，中文放到 `description` 与正文里。

**上界（超了整次调用会被拒）**：`description` ≤1024 字；`body` ≤60000 字符；`files` ≤20 个，单文件 ≤40000 字符且 ≤64KB；SKILL.md + 全部附带文件合计 ≤256KB。附带文件路径必须相对技能目录、不含 `..`、不隐藏目录、层级 ≤3 层。

**正文怎么写**（这一段就是技能的价值所在，写它是给"未来的自己"看的）：

1. **什么时候用我**：触发词（用户会怎么提这件事）、以及明确的"不要用我"指向别的技能；
2. **具体做法**：步骤、参数口径、示例（要能照抄）；
3. **常见坑**：这类任务最容易做错的地方；
4. **交付前自检**：一组能逐条过的检查项。

**写完就生效**：技能清单是每轮现算的，写入后**下一轮对话起**它就在清单里；用户可以 `+ → 引用技能` 点到它。要立刻确认，用 `use_skill` 按名字读回它（你能读到全文 = 已生效）。

**不许占的名字**：内置技能名（`pptx` / `docx` / `xlsx` / `pdf` / `skill-author`）与插件技能目录名会被拒 —— 内置的排在前面，`use_skill` 只会命中内置那份。换个业务前缀（`my-pptx`、`invoice-pptx`）。

**目录长什么样**（真实约定，已在应用里生效）：

```
<用户数据目录>/skills/<技能名>/
├── SKILL.md                 ← 必须有，且必须带 frontmatter（name + description；license 可选）
└── reference/、scripts/…     ← 可选；use_skill 会把文件清单一起给模型
```

**frontmatter 是硬要求**：`SKILL.md` 必须以 `---` 包围的元数据开头。**没有（或没有闭合的）frontmatter
的文件不算技能** —— 加载器会记一条警告后整份忽略：它不进技能清单，`use_skill` 也读不到（等于没装）。
`create_skill` 会替你写好这一段，别事后把它改成裸文本；手写技能目录时也照着上面写。

`<用户数据目录>` 在 Windows 上是 `%APPDATA%\kyclaw`，但**不要自己拼路径**：`create_skill` 已经锁在这个目录里，你给相对路径就行。

## 三、MCP：`add_mcp_server` / `remove_mcp_server`

```
add_mcp_server({
  name: "postgres",              // 面板里显示的名字
  id: "postgres",                // 可选：1-32 位小写字母/数字/短横线（要进工具名 mcp__<id>__<工具名>）
  transport: "stdio",            // stdio：本机起子进程；http：连 Streamable HTTP 地址
  command: "npx",                // stdio 必填
  args: ["-y", "@modelcontextprotocol/server-postgres"],
  env: { "PG_URL": "postgres://…" },
  enabled: false                 // 可省；缺省 false = 只落盘，用户在设置 → MCP 里测试连接后启用
})
```

**两种 transport 的字段**（只认这两种；`sse` 不支持，要 sse 就说明暂不支持并给 http 地址）：

| transport | 必填                                                        | 可选                                                                    |
| --------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| `stdio`   | `command`（启动命令，如 `npx` / `uvx` / `node` / `python`） | `args`（逐个元素的数组，别拼成一整串）、`env`（追加给子进程的环境变量） |
| `http`    | `url`（完整的 `http://` 或 `https://` 地址）                | `headers`（如 `Authorization: Bearer …`）                               |

**id 与工具名**：`id` 只能是小写字母/数字/短横线（1-32 位，不能含 `__`）；不给就按 `name` 派生。它出现在工具名里：`mcp__<id>__<工具名>`。同名 id 已存在 = 覆盖更新。

**启用口径**：新建一律 `enabled: false`（与界面"新增即停用"、插件安装同口径）——先落盘，用户在「设置 → MCP」里点测试连接再启用。**只有配置完整**（stdio 有 command / http 有合法 url）时才允许 `enabled: true`；不完整会回人话让你补。启用后下一轮对话起它的工具以 `mcp__<id>__<工具名>` 出现，**每次调用仍会请求用户审批**（用户可以在设置里把某个工具标成"只读"来免审 —— 这一步留给他，你不要代劳）。

**删除**：`remove_mcp_server({ id: "postgres" })`。只是想停用就别删（让用户在设置里关掉开关）。

**绝不要**：把 API Key 明文写进技能正文或共享给用户的聊天里；把 `readOnlyTools` 当省审批的手段；编一个用户没给的 command / url。

## 四、插件：只能生成目录，安装要用户点

插件体系（市场 + 安装记录 + 把技能复制进用户技能目录）是应用管理的，**你没法替用户安装**。用户给了插件仓库时，两条路：

1. **他只要效果**（推荐）：把插件想给的东西直接落地 —— 技能用 `create_skill`、MCP 用 `add_mcp_server`。效果等价，路径最短。
2. **他明确要"插件"这个形态**（要分发、要出现在插件页列表里）：按下面的真实约定把目录写进他的工作区（用 `write` 工具，路径落在当前会话工作区），然后告诉他：在「插件页 → 添加市场」里填这个**本地目录路径** → 刷新 → 安装。

```
<市场目录>/
├── .claude-plugin/marketplace.json     ← 必须：{ "name": "…", "plugins": [ { "name": "…", "description": "…", "source": "./plugins/my-plugin" } ] }
└── plugins/my-plugin/                  ← 一个插件目录
    ├── .claude-plugin/plugin.json      ← 可选：{ "version": "1.0.0", "mcpServers": … }
    ├── skills/<技能名>/SKILL.md        ← 会被复制进用户技能目录（目录名加插件前缀）
    ├── .mcp.json                       ← 可选：{ "mcpServers": { "名字": { "type": "http", "url": "…" } } }
    └── .claude-plugin/icon.png         ← 可选图标（png/svg/webp/jpg/jpeg，≤256KB）
```

安装后的实际效果（要如实告诉用户）：技能复制到用户技能目录（目录名 = `<插件 id>-<技能名>`）；`.mcp.json` 里的 server 变成设置里的 mcpServers（id 前缀 `plugin-…`，**默认停用**，要在设置 → MCP 里启用）；`commands/agents/hooks` **不会装**（会被静默忽略）。`source` 认 `./相对路径`、`owner/repo`、`{ "source": "github", "repo": "…" }`、`{ "source": "git-subdir", "url": "…", "path": "…" }`、`{ "source": "url" | "git", "url": "…" }`；`archive`/`npm`/`command` 来源会在安装时报"暂不支持"。

## 五、完整走查（用户贴一段说明 → 落地 → 验证）

**用户原话**：

> 帮我装这个 MCP：
>
> ```json
> {
>   "mcpServers": {
>     "filesystem": {
>       "command": "npx",
>       "args": ["-y", "@modelcontextprotocol/server-filesystem", "D:/data"]
>     }
>   }
> }
> ```

**你的步骤**：

1. **先读这份手册**（你已经在读）——不要凭印象写 `command`。
2. **判断类型**：有 `command` → `stdio`；`args` 三个元素逐个放进数组，`-y` 也是。
3. **先跟用户说清**（写在回复里，别只调工具）：「我会在设置里添加 MCP 服务 `filesystem`：命令 `npx -y @modelcontextprotocol/server-filesystem D:/data`，先不启用」。
4. **落盘**：`add_mcp_server({ name: "filesystem", transport: "stdio", command: "npx", args: ["-y", "@modelcontextprotocol/server-filesystem", "D:/data"] })`。
5. **看回执**：拿到「已添加 MCP 服务「filesystem」（id: filesystem，stdio：npx，未启用）…」才算成功；回的是人话错误（比如 `command` 空、`url` 不合法）就按提示补，别重复调同一个参数。
6. **验证生效**：`enabled: false` 时它不在工具表里 —— 这是预期的，告诉用户去「设置 → MCP」点测试连接并启用；如果用户要求**现在就能用**且配置完整，可以再调一次带 `enabled: true`（提示他：这个服务的工具在每轮调用时仍会问他）。
7. **收尾**：一句话总结「装了什么、现在什么状态、下一步在哪儿点」。

**第二个走查（技能）**：

> 用户原话：把这段记成技能：每次我让你做周报，先按上周的模板填数据，再检查三个数字，最后要有一句下周计划。

你的步骤：`create_skill({ name: "weekly-report", description: "用户说\"做周报 / 写周报 / 本周总结\"时用它：按固定模板填数据、核对三个关键数字、补一句下周计划", body: "…把上面这套做法写成步骤 + 常见坑 + 自检…" })` → 回执说「下一轮起在技能清单里」→ 可选：立刻 `use_skill("weekly-report")` 读回确认（能读回就是生效了）→ 告诉用户可以在 `+ → 引用技能` 里点到它。

## 六、什么时候必须让用户确认，什么时候该拒绝

**写之前一定先说清**（审批卡上也要能看懂）：要创建的技能名、要执行的命令、要连的地址、要不要启用。

**先问再动**：用户给的东西里含密钥（token / 密码）—— 告诉他密钥更适合放「设置」里的密钥槽位，MCP 的 `env`/`headers` 会**明文存进 settings.json**，要他明确同意才写；用户给的命令来自不明来源、要 `curl … | sh`、要装全局包 —— 念给他听并让他自己决定（这条走 `bash`，单独审批）。

**直接拒绝**（回人话解释，别说"好的"然后偷偷做）：

- 要求把技能/文件写到工作区外或系统目录（技能只能进用户技能目录、文件只能进工作区）；
- 要求覆盖内置技能名或插件技能目录（工具已经会拒，别绕）；
- 要求你把某个 MCP 工具标成"只读"来免审批 —— 那是用户的决定；
- 要求用插件体系"静默安装"它自己（你做不到，如实说，给出上面的两条路）。

## 七、技能正文怎么写（采纳开源 skill-creator 的写作口径）

这部分决定"未来的模型能不能用好你写的技能"，值得单独讲。

**description 是唯一的触发开关**——技能清单里只给模型 name + description，它靠这两样决定要不要读全文。
所以：

- **"什么时候用"全部写进 `description`**，不要放在正文里（正文只有已经决定要用的模型才看得到）。
- **要"主动"一点**：模型有**少触发**技能的倾向——该用的时候不用。所以别写"如何做一份内部分析看板"，
  要写"……用户提到看板、数据可视化、内部指标，或想展示任何公司数据时都要用，哪怕他没说'看板'两个字"。
  （看我们内置四件套的 description 就知道这个口径：触发词 + 不要用它时该转向哪个技能。）

**正文的四段骨架**（第二节给过一遍，这里说每段写到什么程度）：

| 段           | 写什么                                                      | 别写什么                   |
| ------------ | ----------------------------------------------------------- | -------------------------- |
| 什么时候用我 | 用户会怎么提这件事（原话级触发词）、明确的"不要用我 → 用 X" | 泛泛的"适用于各种场景"     |
| 具体做法     | 步骤、参数口径、能照抄的示例                                | 大段背景介绍               |
| 常见坑       | 这类任务最容易错的地方，每条一句话                          | 罗列所有理论边界           |
| 交付前自检   | 能逐条打勾的检查项                                          | "注意质量"这类没法验证的话 |

**写法**：

- 用**命令句**（"先读 A，再写 B"），不用"建议考虑……"。
- 讲清**为什么**比堆 MUST 有效：说明"名字只能用 slug，因为它同时是目录名与引用名"，
  比"必须使用 slug"更容易被遵守。
- 要固定输出格式就给**完整模板**（"永远用这个结构：`# 标题` / `## 结论` / …"），不要只描述。
- 例子给"输入 → 输出"成对的形式。

**篇幅与分层**：

- **SKILL.md 控制在 500 行以内**；接近上限就再分一层：正文只留主干与"下一步读哪个文件"的指针。
- 超过 300 行的参考文件**开头要有目录**（`use_skill` 会把技能目录的文件清单一起给模型，它按目录决定读哪份）。
- 技能目录的三层约定（我们已经支持）：`SKILL.md` 常驻、`reference/` 按需读、`scripts/` 直接跑不用读进上下文。
  参考资料多就拆成多份，别全塞进 SKILL.md。
- 元数据（name + description）常驻上下文，正文只在触发后才进——所以**信息密度往正文和 reference 里放**。
- **别在正文里写本部署的能力与路径**（"本机装了 PowerPoint 可以渲染""用 `C:\Program Files\…` 里那个程序"
  "我们的模型能看图"）：同一份技能要装在无数台机器上。这类**部署事实**由应用在**加载技能那一刻**拼在
  全文末尾（那段叫「本部署事实」：本机能不能渲染页图、当前模型能不能读图）。正文只写与机器无关的
  "怎么做对"；在正文里判死部署条件，换一台机器就会把模型引到错的做法上。

**一条底线**：技能里不放恶意代码、不放会"用户看了会意外"的内容；用户让你写一段骗人的技能、或专门用来绕过权限的技能，直接拒绝。

## 八、常见坑

- **名字用中文**：`create_skill` 会拒。中文进 `description` 与正文。
- **`args` 拼成一整串**：`"npx -y pkg"` 会被当成一个参数；逐个元素给。
- **把 `-y` 当命令**：`command` 只有可执行名（`npx`），`-y` 属于 `args`。
- **`enabled: true` 但配置不全**：会被拒（这是好事——半个配置启用只会在连接时报错）。
- **说完"帮你装好了"却没有回执**：以工具回执为准；失败的人话里已经写了怎么改。
- **技能正文写成空壳**（只有标题）：技能的价值全在正文，至少写全"做法 + 坑 + 自检"三段。
- **忘了验证**：技能用 `use_skill` 读回、MCP 看回执里的状态行——别只凭"我调过工具了"就下结论。
- **`description` 写成一句摘要**（"这是一个处理发票的技能"）：模型看不出什么时候该用它，技能等于没装。触发词写在 `description` 里，不写正文。
- **手写 SKILL.md 忘了 frontmatter**：那份文件会被**整份忽略**（不进清单、`use_skill` 也读不到），只留一条日志警告。用 `create_skill` 写，或照第二节的形状照抄。
- **正文无限膨胀**：SKILL.md 超过 500 行就该分层，把细节挪进 `reference/`，正文只留主干与指针。
